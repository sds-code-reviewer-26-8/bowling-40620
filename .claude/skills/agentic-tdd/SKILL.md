# Agentic TDD (Human-in-the-loop)

`test-driven-development` 스킬의 규칙(실패하는 테스트 없이는 프로덕션 코드 없음, 실패를 직접 확인, 최소 구현, 초록불에서만 리팩터링)을 **그대로 따른다**. 이 스킬은 거기에 한 가지를 더한다: **각 단계가 끝날 때마다 멈추고, 사람이 검토·승인해야만 다음 단계로 간다.**

이렇게 하는 이유: 사용자는 단계마다 결과물을 직접 읽고 판단한 뒤 **직접 커밋**한다. 그래서 단계 하나가 커밋 하나의 단위가 되고, 에이전트가 앞서 나가면 사용자가 검토하지 못한 변경이 쌓여 커밋 경계가 무너진다.

## 4단계

| # | 단계 | 산출물 | 멈추는 지점 |
|---|------|--------|-------------|
| 1 | Red Plan | `PLAN.md` | 계획 검토 대기 |
| 2 | Red | 실패하는 단위 테스트 | 테스트 검토 대기 |
| 3 | Green | 테스트를 통과시키는 구현 | 구현 검토 대기 |
| 4 | 코드 리뷰 | 리뷰 결과 보고 (필요 시 수정 제안) | 리뷰 확인 대기 |

## 게이트 규칙 (가장 중요)

각 단계를 마치면 **반드시 멈추고** 아래 형식으로 보고한 뒤 응답을 끝낸다.

```
## [단계명] 완료
- 한 일: ...
- 변경/생성한 파일: ...
- 테스트 결과: ... (해당 시)
- 검토해 주세요: <사용자가 특히 볼 포인트>
→ 확인 후 "다음 단계 진행"이라고 알려 주세요. (커밋은 직접 하시면 됩니다.)
```

- **명시적인 진행 지시가 있을 때만** 다음 단계로 간다. "좋아", "ㅇㅋ", "다음", "진행해" 등 분명한 승인은 지시로 본다. 침묵이나 모호한 반응은 승인이 아니다. 애매하면 한 줄로 되묻는다.
- 한 번의 승인은 **바로 다음 한 단계**만 허가한다. 승인받은 단계를 끝내면 다시 멈춘다. "끝까지 알아서 해 줘"라고 명시한 경우에만 그 범위 안에서 연속 진행한다.
- 사용자가 수정을 요청하면 **같은 단계 안에서** 고치고 다시 보고한다. 다음 단계로 넘어가지 않는다.
- **커밋하지 않는다.** `git add`, `git commit`, `git push`도 하지 않는다. 사용자가 직접 한다. 보고 때 변경 파일 목록만 알려 주면 충분하다.
- 이전 단계의 산출물(PLAN.md, 테스트 코드)을 승인 없이 뒤늦게 고치지 않는다. 구현 중 계획이나 테스트가 잘못됐다고 깨달으면 구현을 멈추고 이유를 보고한 뒤 사용자의 판단을 받는다.

## 1단계 — Red Plan: PLAN.md 작성

테스트 코드를 쓰기 **전에** 어떤 단위 테스트를 만들지 `PLAN.md`에 적는다. 사용자가 계획을 먼저 보고 방향을 바로잡을 수 있게 하려는 단계다.

- 위치는 프로젝트 루트의 `PLAN.md`가 기본이다. 사용자가 다른 경로를 지정하면 따른다. `docs/SAMPLE_PLAN.md` 같은 예시가 있으면 먼저 읽고 **그 형식과 톤을 따른다.** 없으면 `assets/PLAN_TEMPLATE.md`를 쓴다.
- 코드베이스를 먼저 읽어 이미 있는 클래스·패키지·테스트 스타일을 파악하고 그에 맞춰 계획한다.
- 테스트 목록은 **가장 쉬운 사례 → 점점 일반적인 사례** 순서로 쓴다. 각 항목은 한 가지 동작만 검증하게 한다.
- 각 테스트마다 이름(동작 설명), 준비(Given), 실행(When), 기대 결과(Then)를 적는다. 구현 방법은 적지 않는다. 계획은 "무엇을 검증하나"이지 "어떻게 만드나"가 아니다.
- 요구사항이 모호하면 추측으로 채우지 말고 PLAN.md의 "열린 질문" 섹션에 적어 사용자가 답하게 한다.
- 이 단계에서는 `src/` 아래 파일을 만들거나 고치지 않는다.

## 2단계 — Red: PLAN대로 단위 테스트 작성

- 승인된 PLAN.md의 테스트를 **계획에 있는 대로** 구현한다. 계획에 없는 테스트를 임의로 추가하거나, 있는 테스트를 임의로 빼지 않는다. 필요하다고 느끼면 보고에서 제안한다.
- 컴파일이 되도록 필요한 빈 껍데기(stub: 클래스·메서드 시그니처, 의미 없는 기본 반환값)만 프로덕션 쪽에 둔다. 동작 구현은 넣지 않는다.
- 테스트를 실행해 **의도한 이유로 실패하는지** 확인한다 (컴파일 오류·오타로 인한 실패는 Red가 아니다). 실행 명령과 실패 메시지 요약을 보고에 포함한다.
- 처음부터 통과하는 테스트가 있으면 그 테스트를 의심하고 보고한다.

실행 명령 (Gradle):
- 전체: `./gradlew test` (Windows는 `gradlew.bat test`)
- 한 클래스: `./gradlew test --tests "패키지.클래스"`
- 한 메서드: `./gradlew test --tests "패키지.클래스.메서드"`

## 3단계 — Green: 테스트를 통과시키는 구현

- Red에서 승인된 테스트를 통과시키는 **가장 단순한 구현**을 쓴다. 테스트가 요구하지 않은 기능이나 추상화는 넣지 않는다.
- 테스트는 고치지 않는다. 테스트가 틀렸다고 판단되면 구현을 멈추고 보고한다.
- 전체 테스트를 실행해 새 테스트와 기존 테스트가 모두 통과하는지 확인하고 결과를 보고에 적는다.
- PLAN의 테스트가 여러 개면, 계획 순서대로 하나씩 Red → Green을 반복하는 편이 안전하지만 단계 경계(커밋 단위)는 사용자가 정한다. 처음 Red 보고 때 "테스트 전체를 한 번에 Red로 쓸지, 하나씩 Red/Green을 오갈지"가 PLAN.md에 정해져 있지 않으면 사용자에게 묻는다.

## 4단계 — 코드 리뷰

방금 만든 테스트와 구현을 **다른 사람의 코드를 보듯** 리뷰한다. 수정은 하지 않고 먼저 보고한다. 사용자가 반영하라고 해야 고친다 (고친 뒤에는 테스트를 다시 돌리고 다시 보고한다).

점검 항목:
- 정확성: 경계값, 예외 상황, 놓친 케이스
- 테스트 품질: 한 가지 동작만 검증하는가, 이름이 의도를 드러내는가, 구현 세부사항에 묶여 있지 않은가
- 단순성: 불필요한 코드·중복·과한 추상화
- 일관성: 기존 코드의 이름·스타일과 맞는가
- PLAN 대비: 계획한 테스트가 모두 구현됐는가, 계획 밖의 변경이 섞이지 않았는가

보고 형식: 발견 사항을 **심각도(꼭 고칠 것 / 고려해 볼 것 / 사소한 것)**로 나누고, 각 항목에 파일:줄 위치와 이유, 제안을 한 줄씩 적는다. 문제가 없으면 없다고 분명히 말한다.

## 사이클 반복

한 사이클(1→4)이 끝나면 다음 기능이 남았는지 사용자에게 묻는다. 다음 사이클도 1단계(Red Plan)부터 다시 시작하며, 기존 PLAN.md는 이어 쓰지 말고 사용자가 정한 방식(덮어쓰기/새 섹션 추가)을 따른다.
